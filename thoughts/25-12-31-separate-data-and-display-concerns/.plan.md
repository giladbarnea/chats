# Plan: Separate Data and Display Concerns (`conversations` / `ccc`)

## Guiding Principle
Postpone formatting + rendering of structured data as late as possible.

- Structured data is malleable.
- Rendering/formatting (XML-ish strings, Rich renderables, ANSI styling) is effectively irreversible.

## Goal
- Fix the `--color=always` bug where thinking/tool blocks disappear (Rich `Markdown()` strips unknown `<...>` tags + their contents).
- Make “what is visible” a single structured source of truth shared by all output modes.
- Ensure XML-ish (`--color=never`) and Rich (`--color=always`) outputs are materially equivalent after ANSI stripping.

## Non-Goals
- Change the external XML-ish schema / tags (`<thinking>`, `<tool-input>`, etc.).
- Redesign CLI flags or output defaults.

---

## Architecture (Data → Render Last)

### 1) Add a structured “visible parts” API on `Message`
Create one data-only API that decides visibility + ordering without serializing:

- `Message.iter_visible_parts(flags) -> Iterable[MessagePart]`

Where `MessagePart` is a small typed structure, e.g.:

- `TEXT(markdown: str)` (from `msg.text`)
- `THINKING(text: str)` (from `msg.thinking`, gated by `--thinking`)
- `TOOL(parts: ToolParts)` (from `msg.tools`, gated by `--tools`)
- `PLAN(parts: ToolParts)` (from `msg.plan`, gated by `--plans`, but represented tool-like to reuse tool rendering)

Key invariant: `iter_visible_parts()` returns **structured** parts only (no `<thinking>...</thinking>` strings).

### 2) Normalize tool rendering once (avoid XML vs Rich drift)
Introduce a single normalization step that captures all formatting decisions as structured data:

- `ToolParts` (dataclass/NamedTuple), e.g.:
  - `tag: str` (`"tool-input"` / `"tool-output"`)
  - `attrs: list[tuple[str, str]]` (ordered; stable output)
  - `body_markdown: str | None` (markdown/fenced blocks; already shortened if needed)
  - `inline_if_empty: bool`

Implement:

- `tool_to_parts(tool: dict, flags) -> ToolParts`

Scope of `tool_to_parts()`:
- Centralize logic currently inside `format_tool_for_xml()` (attrs via `TOOL_SCHEMAS`, special-casing, tool_result code fencing, unknown fallback).
- Represent plan rendering (`ExitPlanMode`) as `ToolParts(...)` so it flows through the same renderer(s).

Then implement two thin renderers consuming `ToolParts`:

- `render_tool_xml(parts: ToolParts) -> str`
- `render_tool_rich(parts: ToolParts) -> list[RenderableType]` (`Text` for tags + `Markdown` for body)

### 3) Make XML/JSON/search consume parts (render at the end)
Add a single “inner XML-ish” renderer that converts parts → string at the last moment:

- `render_message_inner_xml(msg: Message, flags) -> str`

Update internal flows to depend on structured parts, not `get_visible_content()`:

- `format_to_xml()` → uses `render_message_inner_xml()` for inner content, then wraps with outer message tag/header.
- `format_to_json()` → preserves schema but uses `render_message_inner_xml()` for `content`.
- `cmd_search()` → uses the same rendered “visible text” source to match against.

Optional compatibility:
- Keep `Message.get_visible_content()` as a thin wrapper calling `render_message_inner_xml(self, flags)`, but treat it as legacy (no internal call sites).

### 4) Rewrite Rich rendering to never pass tags to `Markdown()`
Refactor `render_messages_with_rich()` to operate on `Message` + structured parts:

- Outer open/close tags: `Text(..., style="dim")`
- Header: `Text(..., style=wrapper_type.value.rich_style)`
- Per-part:
  - `TEXT` → `Markdown(markdown)` (only place `Markdown()` is used for message content)
  - `THINKING` → open/close tags as dim `Text`; body as `Text(..., style=ContentBlockType.THINKING.value.rich_style)`
  - `TOOL/PLAN` → `render_tool_rich(tool_parts)` (tags as dim `Text`, body as `Markdown(body_markdown)` when present)
- Insert the same message separator used by the non-colored path (so comparisons are meaningful).

Invariant: Rich `Markdown()` never receives any `<...>` tags.

---

## Implementation Steps (Concrete)
1. Add `MessagePart` (+ enum/typing) and `ToolParts`.
2. Implement `tool_to_parts()` and the two tool renderers (`render_tool_xml`, `render_tool_rich`).
3. Implement `Message.iter_visible_parts(flags)` (single source of truth for visibility/order).
4. Implement `render_message_inner_xml()` (parts → string).
5. Refactor `format_to_xml()`, `format_to_json()`, and `cmd_search()` to use parts + renderers (not `get_visible_content()`).
6. Refactor `render_messages_with_rich()` to consume parts and keep tags out of `Markdown()`.
7. Keep/convert `get_visible_content()` to a wrapper (optional), ensure nothing internal depends on it.

## Test Plan
Add a regression test that would have failed before:

- Run `ccc` with `--color=always` while piped (mirrors real usage), strip ANSI in-test.
- Assert thinking/tool content survives (e.g., using `tests/data/synthetic_flags.jsonl`):
  - With `--thinking`: output contains `<thinking>` and known thinking text.
  - With `--tools`: output contains `<tool-input` / `<tool-output>` and known tool payload.
- Keep the existing “ANSI present vs absent” checks, but add “content parity” checks.

## Acceptance Criteria
- `--color=always` and `--color=never` produce the same logical content (no missing thinking/tool/plan blocks).
- “What is visible” logic exists in exactly one place (`Message.iter_visible_parts()`).
- Tool formatting decisions exist in exactly one place (`tool_to_parts()`), consumed by both XML and Rich renderers.
